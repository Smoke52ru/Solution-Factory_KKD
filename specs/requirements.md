# Требования: страница модуля ККД

Источники: [`docs/Тестовое_задание_Frontend.pdf`](../docs/Тестовое_задание_Frontend.pdf), [`docs/БТ-трекер целей.pdf`](../docs/БТ-трекер%20целей.pdf), [`docs/UI-KIT.md`](../docs/UI-KIT.md), контракт mock API в [`backend/app/main.py`](../backend/app/main.py). Как это реализуется — в [`design.md`](design.md).

## 1. Что делает решение

Страница модуля **контроля качества данных (ККД)** по целям и ключевым результатам. Данные берутся из готового mock API; бэкенд не пишется. Руководитель за несколько секунд должен понять две вещи:

1. стало лучше или хуже по сравнению с прошлым прогоном;
2. что исправлять в первую очередь.

Страница состоит из:

- **контекста** — выбор подразделения и прогона, подпись «с каким прогоном сравниваем»;
- **сводки** — вердикт по главной метрике, карточки метрик с прошлым значением, дельтой и оценкой «лучше / хуже», счётчики `new / persisting / resolved`, разбивка проблем по важности и правилам;
- **таблицы проблем** — серверные фильтры и пагинация;
- **карточки проблемы** — описание, факт и ожидание, рекомендация, история по прогонам.

Все числа берутся из ответов API как есть. Фронтенд ничего не пересчитывает: он только выбирает подпись, цвет и стрелку по полям `trend`, `higher_is_better`, `delta`.

## 2. Пользователи и user stories

Аудитория: администраторы системы, руководители департаментов и ответственные за целеполагание в подразделениях. Проверка планируется еженедельно.

| ID | История |
|---|---|
| US-1 | Как пользователь сервиса, я хочу видеть количественные и качественные метрики по набору данных (цели и ключевые результаты) с учётом каскадирования. |
| US-2 | Как пользователь сервиса, я хочу видеть динамику (дельту) относительно предыдущего набора данных, полученного в прошлый раз. |
| US-3 | Как руководитель, я хочу выбрать подразделение и прогон и увидеть всю страницу для этого контекста, не перезагружая её. |
| US-4 | Как руководитель, я хочу сразу увидеть, с каким прогоном идёт сравнение, чтобы не принять дельту за сравнение с неизвестной точкой. |
| US-5 | Как ответственный за целеполагание, я хочу видеть, что исправлять в первую очередь: самые важные проблемы и правила, по которым их больше всего. |
| US-6 | Как ответственный, я хочу отфильтровать проблемы по правилу, важности и статусу дельты и листать их постранично. |
| US-7 | Как ответственный, я хочу по клику на счётчик `new / persisting / resolved` открыть список проблем с этим фильтром. |
| US-8 | Как ответственный, я хочу открыть карточку проблемы: что не так, какое значение ожидалось, что делать и как проблема вела себя в прошлых прогонах. |
| US-9 | Как пользователь, я хочу, чтобы при ошибке, медленном ответе или пустом результате интерфейс объяснял, что происходит, и не ломался. |
| US-10 | Как пользователь, я хочу делиться ссылкой на страницу в конкретном состоянии (подразделение, прогон, фильтры, страница, открытая проблема). |

## 3. Критерии приёмки по функциям

### 3.1 Контекст (US-3, US-4, US-10)

- **CTX-1.** Подразделение выбирается в дереве, построенном из `units[].parent_id` из `GET /api/meta`. Выбранное подразделение показано хлебными крошками из `unit.path` ответа сводки.
- **CTX-2.** Прогон выбирается из `GET /api/runs`. Каждый пункт содержит номер, дату (`snapshot_date`) и статус **словом** (не только цветом): «Успешно», «Ошибка», «Выполняется». Неуспешный и выполняющийся прогон выбрать можно.
- **CTX-3.** Если в URL нет параметра `run`, используется первый прогон со статусом `completed`. В запросах всегда уходит явный `run_id`, а не `latest`.
- **CTX-4.** Если в URL нет параметра `unit`, выбирается подразделение `B2B` — корень оргструктуры; в URL оно не записывается.
- **CTX-5.** Смена подразделения или прогона обновляет сводку и таблицу без перезагрузки страницы, сбрасывает пагинацию (`page`) и закрывает карточку проблемы (`issue`). Фильтры сохраняются.
- **CTX-6.** Под селекторами показана подпись сравнения из `compared_to`: «RUN-008 от 26.10.2026 сравнивается с RUN-007 от 19.10.2026». Если `compared_to` равен `null`: «Первый прогон — сравнивать не с чем».
- **CTX-7.** Всё состояние страницы лежит в query-параметрах URL: `unit`, `run`, `rule`, `severity`, `status` (одно значение), `q`, `page` (с 1), `issue`; открытие ссылки восстанавливает то же состояние. Значения по умолчанию в URL не пишутся; ввод в поиск (с задержкой 400 мс) не добавляет записей в историю браузера. Точная схема — в [`design.md`, раздел «Состояние в URL»](design.md#4-состояние-в-url).
- **CTX-8.** Если `unit` из URL нет в `meta.units`, запросы сводки и проблем не выполняются; вместо них один `Result` «Подразделение {id} не найдено» с кнопкой «Открыть {имя корня}» (для `B2B` — «Открыть Корпоративный блок»). Если `run` из URL нет в списке прогонов — один `Result` «Прогон {id} не найден» с кнопкой «Открыть последний успешный прогон» (если такой есть).

### 3.2 Сводка (US-1, US-2, US-5)

- **SUM-1.** Первым на странице виден вердикт: метрика `clean_goals_share` крупным числом, слова «Стало лучше / Стало хуже / Без изменений» по её `trend` (только если есть `previous` и `trend`), стрелка с дельтой и «было X в RUN-NNN».
- **SUM-2.** Остальные метрики показаны карточками: значение как в API (`0` → «0 шт.»), «было X» (`previous`, если не `null`), дельта и `delta_pct`. «—» и подпись «нет данных» — только при `value === null`. Формула метрики (`formula`) доступна в подсказке, в том числе с клавиатуры.
- **SUM-3.** Дельта показывается по правилам из [`design.md`, раздел «Правила дельты»](design.md#правила-дельты): цвет и текст «лучше / хуже» зависят от `trend`, а не от знака числа; стрелка показывает направление `delta`. При `delta === 0` — нейтральное «без изменений» без иконки минуса и без «0 шт.».
- **SUM-4.** Счётчики `new`, `persisting`, `resolved` — кнопки (`aria-pressed`); клик задаёт фильтр статуса дельты (`status`) и прокручивает страницу к таблице, повторный клик по активному счётчику снимает фильтр.
- **SUM-5.** Блок «Что исправлять в первую очередь» показывает только строки `issues_by_severity` и `issues_by_rule` с `current > 0`, отсортированные по важности (`meta.severities[].order`), затем по `current`. Клик по правилу фильтрует таблицу по этому правилу (`rule`) и прокручивает к ней. Числа не пересчитываются. У строк этого блока нет `trend`, поэтому их дельта нейтральная: стрелка по знаку и число без слов «лучше / хуже»; при `delta === 0` — «без изменений»; при `previous = null` — «нет данных для сравнения». Если проблем нет, блок показывает «Проблем не найдено».
- **SUM-6.** Важность всегда подписана словом и значком, а не только цветом.
- **SUM-7.** Признак «в подразделении нет целей» (`hasNoGoals`): `goals_active.value === 0` или `clean_goals_share.value === null`. Тогда вместо вердикта и счётчиков — `Empty` «В подразделении пока нет целей — проверять нечего», блок «Что исправлять» скрыт.

### 3.3 Таблица проблем (US-6, US-7)

- **ISS-1.** Фильтры: правило и важность (множественный выбор из `meta.rules` и `meta.severities`), статус дельты (один из «Все / Новая / Сохраняется / Исправлена»), поиск по тексту `q` (ID, название, ответственный; запрос уходит после паузы 400 мс). Фильтрация выполняется сервером. Кнопка «Сбросить фильтры» в панели неактивна, пока фильтров нет.
- **ISS-2.** Пагинация серверная: `limit`, `offset`, `total` из ответа. Размер страницы — 20; номер страницы — в URL (`page`, с 1). Пагинатор скрыт, если всё помещается на одной странице. Если `page` из URL вышел за пределы выдачи, он заменяется на 1.
- **ISS-3.** Колонки: важность, правило, объект (цель или КР с ID), подразделение, ответственный, статус дельты (тег со словом), «подряд N прогонов». `runs_in_row` у `resolved` — `null`, показывается «—».
- **ISS-4.** Строка открывается кликом или с клавиатуры (Enter, пробел); при этом в URL появляется `issue`.
- **ISS-5.** При смене страницы или фильтра прежние данные остаются на экране с индикатором загрузки; таблица не мигает.
- **ISS-6.** Статус `resolved` приходит от API только при явном фильтре `delta_status=resolved`; поэтому в списке без фильтра исправленных проблем нет, и это ожидаемо. В первом прогоне вариант «Исправлена» отключён, а `status=resolved` из URL игнорируется.

### 3.4 Карточка проблемы (US-8)

- **MOD-1.** Модальное окно открывается по `issue` в URL. Закрытие: если карточку открыли внутри приложения — `navigate(-1)`; если по прямой ссылке — `issue` убирается из URL через `replace`.
- **MOD-2.** Заголовок окна — `rule_title` (пока данные грузятся — «Карточка проблемы»); id проблемы — вторичным текстом в теле. Содержимое: описание (`details`), факт (`actual`) и ожидание (`expected`), рекомендация, ответственный (`owner.full_name`, должность), когда впервые обнаружена (`first_detected_run_id`, `first_detected_at`), история по прогонам.
- **MOD-3.** В истории для каждого прогона явно указано, была ли проблема: «Проблема есть» (`present: true`) или «Проблемы нет» (`false`); выбранный прогон помечен тегом. При `present === null` показано «Ошибка прогона — состояние неизвестно» (`failed`), «Прогон выполняется — состояние неизвестно» (`running`) или «Нет данных», а не пустое место.
- **MOD-4.** Для `actual` или `expected`, равных `null`, показывается «—».
- **MOD-5.** Ответ 404 `ISSUE_NOT_FOUND` показывается сообщением «Проблема не найдена» внутри модалки; страница не ломается. Прочие ошибки — `ErrorState` внутри модалки.

## 4. Критерии приёмки по граничным состояниям

| ID | Состояние | Данные | Ожидаемое поведение |
|---|---|---|---|
| **RUN-001** | Первый прогон | `compared_to = null`; у метрик `previous`, `delta`, `delta_pct`, `trend` равны `null`; у `delta` (счётчиков) значения `null` | Везде вместо дельты — «нет данных для сравнения» цветом `colorTextTertiary`, ни одного «0». Подпись сравнения: «Первый прогон — сравнивать не с чем». Счётчики `new / persisting / resolved` заменены одной подписью и не кликабельны. В фильтре статуса значение `resolved` отключено, рядом пояснение. |
| **RUN-006 / 409 RUN_FAILED** | Неуспешный (`failed`) или выполняющийся (`running`) прогон | Статус берётся из `GET /api/runs`; для такого прогона API отвечал бы 409 `RUN_FAILED` / `RUN_IN_PROGRESS`; причина — `run.error` | Запросы сводки и проблем **не выполняются**. Вместо сводки и таблицы — `Result`: для `failed` «Прогон RUN-006 от <дата> завершился с ошибкой» и причина, для `running` «Прогон … ещё выполняется»; кнопка «Открыть последний успешный прогон» (если такой есть). Селекторы контекста остаются рабочими. Прогон помечен в списке тегом «Ошибка» / «Выполняется». |
| **TX-NEW** | Подразделение без целей | Признак: `goals_active.value === 0` **или** `clean_goals_share.value === null` (`hasNoGoals`) | Вместо вердикта и счётчиков — `Empty` «В подразделении пока нет целей — проверять нечего»; блок «Что исправлять» скрыт. Карточки метрик показывают значения API как есть (`0` → «0 шт.»); «—» / «нет данных» — только при `value === null`. Таблица проблем — нейтральный `Empty` «В подразделении пока нет целей» без зелёной галочки. |
| **Неизвестный unit** | `unit` нет в `meta.units` | Например `?unit=NOPE` | Один `Result` «Подразделение NOPE не найдено», кнопка «Открыть Корпоративный блок»; сводка и проблемы не запрашиваются. |
| **Неизвестный run** | `run` нет в списке прогонов | Например `?run=RUN-999` | Один `Result` «Прогон RUN-999 не найден», кнопка «Открыть последний успешный прогон»; сводка и проблемы не запрашиваются. |
| **TX-SAL** | Нет проблем | `issues_total = 0`, таблица пуста без фильтров | Позитивное пустое состояние «Проблем не найдено» (значок успеха, без кнопки сброса); в блоке «Что исправлять» — «Проблем не найдено». Это не ошибка и не «ничего не найдено по фильтру». |
| **Загрузка** | Ответ с задержкой (~300 мс и больше) | Запрос в процессе | Сводка и первая загрузка таблицы — `Skeleton`; при смене страницы или фильтра таблица — `loading` поверх прежних данных. Если ответ идёт дольше 3 секунд — подсказка «Загрузка занимает больше обычного». |
| **Ошибка сети** | Нет ответа, таймаут, 5xx | `ApiError` с кодом `NETWORK_ERROR` или 5xx | Блок `ErrorState` с понятным текстом («Нет связи с сервером», «Сервер временно недоступен») и кнопкой «Повторить» (`refetch`); перед этим выполняется один автоматический повтор. Ошибка одной секции не ломает остальные: сводка и таблица загружаются и падают независимо. Ошибки 4xx — `ErrorState` без «Повторить». |
| **Пустой фильтр** | Фильтры заданы, `total = 0` | Таблица пуста | `Empty` с текстом «По выбранным фильтрам проблем не найдено» и кнопкой «Сбросить фильтры» (сбрасывает `rule`, `severity`, `status`, `q`, `page`). |
| **404 по проблеме** | Неизвестный `issue` в URL | 404 `ISSUE_NOT_FOUND` | Сообщение «Проблема не найдена» в модалке, закрытие убирает `issue` из URL. |

## 5. Нефункциональные требования

- **Соответствие UI-киту.** Тема собрана из токенов [`UI-KIT.md`](../docs/UI-KIT.md) и подключена через единственный `ConfigProvider`. Цвета в компонентах берутся из темы (`theme.useToken()`), hex в компонентах не используются. Текст 14/22, заголовки 20/600/28, радиусы: карточки 8–16, модалка 28; высота контролов 32; отступы кратны 4. Шрифт Inter. Ant Design 5.
- **Доступность (a11y).** Семантическая разметка: шапка приложения (`Header`, название — обычный текст), `main` страницы с h1 «Контроль качества данных» (`<main>` задаёт страница, а не обёртка приложения), `section` с `aria-labelledby`. Счётчики и строки правил — кнопки с `aria-pressed`. Важность и направление дельты передаются текстом и значком, не только цветом. У `DeltaIndicator` есть `role="img"` и `aria-label` с полной фразой («Снизилось на 4,3 п.п. относительно RUN-007 — хуже»). Строки таблицы и модалка доступны с клавиатуры, фокус виден.
- **Без пересчёта на фронтенде.** Значения метрик, предыдущие значения, дельты, проценты и счётчики отображаются ровно как в ответе API. Сортировка блока «что исправлять» меняет только порядок вывода.
- **Адрес API из окружения.** `VITE_API_URL` (пусто — относительные `/api`), в компонентах адрес не прописан.
- **Без дублирования запросов.** Один запрос на один набор параметров; единая фабрика ключей кеша; `meta` — `staleTime: Infinity`; список `runs` — `staleTime` 60 с и опрос каждые 3 с, пока в списке есть прогон со статусом `running`.
- **Десктоп от 1280 px.** Содержимое до 1440 px по центру.
- **Запуск одной командой.** `docker compose up --build` поднимает mock API и фронтенд; страница доступна на http://localhost:8080. В README — не более трёх команд.
- **Не требуется:** авторизация, свой бэкенд, SSR.
- **Тесты** (плюс, не обязательно): Vitest + Testing Library, `npm test`. Покрыты `DeltaIndicator` (все ветки `trend` и `null`, нулевая дельта), приведение ошибок API, форматирование, `useKkdParams` (разбор URL, сброс пагинации, закрытие карточки), пустые состояния таблицы (в том числе `noGoals`) и сценарии страницы RUN-001, TX-NEW, RUN-006, неизвестные `unit`/`run`. Подробный список — в [`design.md`, раздел «Тесты»](design.md#11-тесты).
- **Спецификации** актуальны: при изменении решения обновляются оба файла.
